## 阶段一：推送与 CI 解锁（本地，2026-10-15 凌晨）

推送 36 个提交（七批次 + 自查修复 + 教程站归档）后触发 workflow_dispatch 部署，CI 连续暴露三个被历史掩盖的问题（CI 自 2026-10-10 起一直红，七批次期间只做了本地验证）：

### 1. assistant 依赖锁漏 aiohttp 闭包（致命，阻塞 pip check）

- 现象：CI 全新环境 `pip check` 红——`smartlect-assistant 0.1.0 requires aiohttp, which is not installed`。
- 根因：2026-10-10 修线上 ES 静默跳过时在 pyproject 显式声明 `aiohttp>=3.9`（见注释），但**漏改 `requirements.lock`**；线上 venv 手工补装掩盖了缺口，本地 venv 同样装过所以三栈自检不红。与 cicd.md 记录的 2026-09-19 langfuse 锁漂移同型。
- 修复：`requirements.lock` 补 7 钉（aiohttp==3.14.4 及闭包 aiosignal/attrs/frozenlist/multidict/propcache/yarl，版本取自本地通过全量测试的 venv 冻结），锁头注释记录来龙去脉。
- 验证：全新 venv `pip install -r requirements.lock` + `--no-deps ./assistant` + `pip check` 干净 + 336 项单测过（跳过 68 项 MySQL 契约）。

### 2. shopping 预算测试漏同步默认 8（高，阻塞 MySQL 契约测试）

- 现象：`SMARTLECT_RUN_MYSQL_TESTS=1` 下 `test_six_actual_attempts...` 红——`actual_attempts 8 != 6`。
- 根因：2026-10-10 18:04 提交 43c23eb 把 `MODEL_CALL_LIMIT` 默认 6→8（90 秒回合硬约束的折中），**没同步该测试**；当天 11:40 CI 已被上面的 pip check 挡红、此后 CI 再没跑过，漏更新测试从未被发现。本地复跑确认确定性失败，与七批次无关（七批次未动 assistant 源码）。
- 修复：测试改名 `test_eight_actual_attempts...`，断言对齐实际行为（8 次尝试 = 4 轮×[失败+成功]、`len(messages)==4`——预算耗尽后不再开第 5 轮窗口，直接 rule-fallback 收口）。测试语义不变：重试消耗预算、fallback 不重置预算。附带修正 `session.py` 中误导性的 "default 6" 陈旧注释。
- 验证：`test_shopping_mysql.py` 全文件 MySQL 契约模式 37 项全绿。

### 3. 代码卫生（响应用户"终版干净、无死代码"要求）

- `STATUC_SUCCESS/STATUC_ERROR` 拼写错误常量全量改名 `STATUS_*`（3 文件 15 处；批次六登记过该卫生项但未落实，本次直接改净，不留弃用别名双版本）。
- `LocalMessageOutboxMapper` 删除 `markRetriesExhausted`/`selectDispatchBatch` 的死参数 `now`（批次六 DB 时钟改造后 XML 已全用 `NOW()`，接口参数成残留），同步清理实现与 3 处测试调用。
- 复核：七批次声明删除项全部删净（PayTradeInitiated/releaseOrderDeductKey/sendHighConcurrency 分支/file.conf/feign-rules-enabled 键均无残留，仅解释性注释）；`replayExhausted` 非死代码（由 `POST /internal/mq/outbox/{id}/replay` 暴露）。
- 验证：`mvn test -pl smartlect-common -am` 125 项全绿。

### 4. Sentinel Nacos 数据源线上启用通道（落实方案③）

`smartlect-common.yml`/gateway `application.yml` 的规则 data-id 键从注释示例改为 env 占位（`${SMARTLECT_SENTINEL_{GATEWAY,DUBBO}_RULES_DATA_ID:}`）：仓库默认关（代码兜底规则），生产经 `runtime.env` 启用。线上启用后暴露缺陷 B（见下）。

## 阶段二：CI 部署 node1

### 第 3 次部署被 coupon 装配缺陷拦截 → 加冒烟防线 → 第 4 次成功

- **失败形态**：`mvn package` 成功，`systemctl restart smartlect-apps` 停在 coupon——启动即退，`CouponInternalService` 注入失败：`A component required a bean of type 'java.util.concurrent.ExecutorService' that could not be found`。
- 根因：批次四把 `CouponCacheExecutorConfig` 的 Bean 定义改为 `ThreadPoolTaskExecutor`（返回类型 `Executor`），但 `DiscountCouponCacheComponent` 仍按旧类型 `ExecutorService` 注入——`mvn test` 全 mock 单测拦不住装配期错误，只有真实上下文刷新能暴露（与 2026-09-16 教训同根）。
- 修复（提交 b6706f4）：注入类型对齐 `Executor`。
- **系统性防线**：`ci-deploy.sh` 在停机前增加 `runtime.py smoke` 启动冒烟（坏 JAR 在整站停机前拦下）。仓库副本 `run/cloud/ci-deploy.sh`（未跟踪）与服务器 `/root/deploy/ci-deploy.sh` 同步更新（服务器留 `.bak-20261015` 备份）。
- 第 4 次部署成功（run 38609295717）：冒烟 9 服务全过 → `apps-check: 12 owned healthy processes, 9 Nacos registrations` → `DEPLOY-OK 15726ac -> b6706f4`。

## 阶段三：集群同步与线上验证（node2/3 切换 + 六缺陷）

CI 只部署 node1（仓库设计如此）；node2/3 是 sync-app-node.sh 分发的 JAR 副本节点，本阶段完成两从机切换并暴露/修复六个缺陷。

### node2/3 切换与遗留状态纠正

两机 `smartlect-apps` 单元此前为 failed 态（10-14 修 ES 绑定后应用是手动拉起的，脱离 systemd 托管；node2 还有 3 个 10-14 遗留的旧版本孤儿进程），本次一并纠正：停单元 → `reset-failed` → 清孤儿进程 → sync 新 JAR/scripts/runtime.env/单元 → `systemctl start`。两机启动后 5 服务（gateway/product/order/user/cart）健康 200、Nacos 各 5 注册。

### 缺陷 A：sync 覆盖节点特有 env——ES/QDRANT 地址被写回 127.0.0.1（阻塞 node2 product 健康）

- 现象：node2 重启后 product `Health timeout`（恰好 240s），日志 `Elasticsearch health check failed: Connection refused`。
- 根因链：10-14 修「ES 内网绑定」时把**两副本 env 的 ES_URL/QDRANT_URL 改指 172.21.131.151**（只存在于从机 runtime.env）；而 `sync-app-node.sh` 按「副本与 node1 一致」设计整体覆盖 runtime.env，只重写 4 个 override 键——10-14 那次手改的节点特有值被同步覆盖回 `127.0.0.1`。同时发现 node1 env 里 `SMARTLECT_ES_URL` 存在重复行。
- 修复（根治而非打补丁）：node1 的 runtime.env 把 `SMARTLECT_ES_URL/QDRANT_URL` 统一改为内网 IP `172.21.131.151`（与 MySQL/Redis/RocketMQ/Nacos 同一惯例——这些地址本就是集群通用的），并去掉重复行；sync 的既有设计由此恢复成立。node1 自身经双绑定验证 200/200 可达后切换。

### 缺陷 B：Sentinel Nacos 数据源 403——挂接成功但规则永远为空

- 现象：node2 product 日志 `dataId=smartlect-sentinel-dubbo-rules.json ... errorCode=403, message='user not found!'`；此时规则是「挂接成功→跳过代码兜底→Nacos 取不到→空规则」。
- 根因：`NacosDataSource(serverAddr, group, dataId, converter)` 裸构造不带鉴权，开 auth 的集群 Nacos 一律 403。本方案启用通道（阶段一 §4）线上首次启用即暴露。
- 修复（提交 9b1c47a）：`DubboSentinelRulesConfig` 与 `SentinelGatewayConfig` 改用 `Properties` 构造并带配置中心同源凭据（`spring.cloud.nacos.config.username/password/namespace`）。common+gateway 模块测试 125+15 全绿。
- 验证：重启后两处皆 `已挂接 Nacos 数据源`，日志 403 数为 0。

### 缺陷 C：xxl-job-admin OOMKilled 停摆 19 小时——全部 @XxlJob 任务静默停摆

- 现象：排查 outbox 卡住消息时发现 `smartlect-xxl-job-admin-1` 容器 `Exited (137)`、`OOMKilled=true`，死亡时刻 **10-14 07:39**（RestartPolicy=no 一直未起）——outbox 定时兜底投递/支付轮询/退款对账/补偿重放等 **10 个 @XxlJob 任务全部没在跑**（新消息靠 afterCommit 即时投递照常，所以此前未被发现）。
- 根因：compose 给了 `mem_limit: 512m` 但未定 JVM 堆；镜像为 openjdk 8u342，非堆增长顶爆 cgroup。
- 修复（提交 b6a2fe1）：compose 增加 `JAVA_OPTS: "-Xms256m -Xmx256m"`（对齐 ES 的 heap=limit/2 惯例）+ `restart: unless-stopped`（OOM 自愈，杜绝再次长时间静默停摆）。node1 以 runtime.py 同款 compose 调用重建容器。
- 验证：容器 healthy；执行器在 1 分钟内注册；任务定义 10 个 cron 在位。

### 缺陷 D：定时消息 24h 时间轮上限——7 天确认收货消息必被拒、必转 EXHAUSTED（本项目级缺陷）

- 现象：outbox 消息 `pay:confirm:20261014...`（订单 202610140633202302Ugu1bnqEpluHtf，已发货）自 10-14 07:33 创建后 10 次重试耗尽转 EXHAUSTED；重放后仍失败：`BadRequestException: response-code=40012 the max delay time of message is too large, max is 86400000`。
- 根因：`CONFIRM_RECEIPT = Duration.ofDays(7)`，broker 定时消息（时间轮）单条最大延迟 24h——**任何 7 天延迟消息在创建时刻就超出上限**，10 次重试分钟级耗尽（"多次重试后自动收敛"对该档不成立）。此前 e2e（15min/1h 档）未覆盖 7 天档所以未暴露。10-14 的"迁移窗口耗尽"表象下，真正必然后果是：**每一笔走到发货的订单，其确认收货事件都会耗尽进 EXHAUSTED**。
- 候选修法：①提高 broker 上限——5.3.2 时间轮该校验无用户配置项，不可取；②放弃 MQ 仅靠 `orderAutoReceiptReconcile` 对账——与设计（双路径）不符；③**Outbox 层"时间轮驻留"（采用，提交 28624bf）**：距到期超过上限时不投，把 `next_retry_time` 推到「到期 - 上限 + 60s 安全余量」，由 5s 兜底投递在临近时刻重投，彼时剩余延迟已在上限内。判定与写入全部用数据库时钟（延续批次六纪律），重复驻留等价幂等。
- 落点：`LocalMessageOutboxMapper.parkUntilTimerHorizon` + `OutboxMessageServiceImpl.tryDispatch` 驻留分支 + 配置键 `mq.outbox.timer-horizon-ms`（默认 86400000）。单测 2 例 + 真库 IT（驻留值/重复幂等/近未来不驻留/用例表隔离）。
- **语义**：送达时刻不变（创建+7 天），投递机制从"一条超长定时"改为"驻留到进入时间轮后一次性投递"。
- 生产验证（部署后实测）：`POST /internal/mq/outbox/18037/replay` 返回 success，消息 `status=0, retry_count=0, next_retry_time=2026-10-20 07:34:50`（=10-21 07:33:50 − 24h + 60s），零 40012。**最终送达与自动确认收货在 2026-10-21，留作未来验收**。

### 缺陷 E：node1 根分区被历史暂存 JAR 撑满 100%——冒烟永久挂起、部署被 job 超时取消（本项目级事故）

- 现象：28624bf 的部署在冒烟步骤**无输出挂起 29 分钟**，被 deploy job `timeout-minutes: 30` 自动取消（未执行重启）；jstack 追挂起冒烟 JVM：主线程停在 coupon 一条 MySQL 语句等响应 27 分钟（`TrialCouponSeedService` @PostConstruct 种子），dump MySQL 进程列表反被 `ERROR 1114: The table '/tmp/#sql...' is full` 打脸——**MySQL 临时表分配失败**。
- 根因链：根分区 **40G 用满 100%**。大头是 `/opt/smartlect/run/apps` **14G**——`immutable_jar` 每次启动按构建哈希暂存 JAR 副本（9 服务 × ~160MB × 多日多轮部署），旧版本从不回收（原注释"retain old hashes; prune only inactive snapshots if disk usage matters"——本次就是那个时刻）。满盘后果：MySQL 临时表建不出 → 语句无限等待 → 冒烟挂起；而 smoke 读循环是**阻塞 readline**，无新行输出时 deadline 永不触发，整个部署悬挂。
- 修复（三层）：
  1. **止血**：清 run/apps 非台账引用快照（保留运行中版本 + 10 分钟宽限），释放 **13.2G**（100%→68%），MySQL 立即恢复。
  2. **根治（runtime.py）**：`prune_staged_artifacts()` 在 `apps_up`/`smoke_apps` 收尾自动回收；**首跑实证** `pruned staged artifacts: 1336 MB`。
  3. **防线**：smoke 读循环改**读线程 + 轮询 + 截止强制**；`ci-deploy.sh` 增加 **5G 磁盘门禁**；deploy job 超时 30→40 分钟。
- **修复过程中的一次自伤与迭代（诚实记录）**：读线程化改造把 `finally` 写成 **close-before-terminate**——读线程阻塞在空管道 read() 时持有缓冲锁，主线程 `close()` 永远等锁（服务器最小实验复现：15s 未返回）。前 8 个服务因运行期有周期日志释放锁而侥幸通过，**gateway（反应式、启动后无周期日志）第一个踩中**，冒烟 29 分钟不动。修复：**terminate-first**（终止子进程→读线程收 EOF 释放锁→再关流），复现实验 0.00s 返回；提交 8234d2f，其后部署 smoke 全过（gateway 12s）。

### 缺陷 F：node2/3 的 xxl-job 执行器从未注册——调度中心地址默认 127.0.0.1（同类集群寻址缺口）

- 现象：三机切换后核查注册表，smartlect-order/product/user/cart 执行器**只有 node1** 注册；node2 现场 `TCP-OK` 连通 admin:18090 但日志持续 `Connection refused`。
- 根因：`xxl.job.admin.addresses` 默认 `${SMARTLECT_XXLJOB_URL:http://127.0.0.1:18090/xxl-job-admin}`，runtime.env 从未配置该键——副本连本机 18090（无监听），与缺陷 A 同类。
- 修复：node1 env 增加 `SMARTLECT_XXLJOB_URL=http://172.21.131.151:18090/xxl-job-admin`（node1 实测内网地址 302 可达），随 sync 下发并重启 node2/3。
- 验证：cart/order/product/user 各 **3 机各一执行器**；admin/coupon/pay/stock 仅 node1（服务本就不在副本节点）。修复前任务全部由 node1 执行（功能不受损），本条消除"node1 对应服务宕机则任务无执行器"的可用性缺口。
