## 根因与修复

### 1. 展厅身份判定误把超管算进去（本地验收暴露，影响面最大）

`TrialAdminAccess.isTrial` 只看"有 `admin:trial` 权限点"，而超管（SUPER_ADMIN）持有**全部**
权限点 → 凡在拒绝清单里的超管操作（发货/改分类/改用户状态/券写…）全部被守卫 403
"作品集展厅账号只能…"。本地实测：超管写券被 403。

- 修：守卫改用权威判定 `TrialIdentities.isTrialAdmin`（account==gallery 或 role==TRIAL_OPERATOR，
  含 admin:legacy/SUPER_ADMIN 豁免）；`isTrial` 同步加豁免并与权威口径对齐（注释交叉引用）。
- 测试此前用不真实的权限集合（缺 `admin:trial`）恰好绕过误判路径——补回归用例：
  `TrialAccessTest` 改写为身份判定套件（含"超管+全部权限点"用例）、`TrialAdminAccessTest`
  增 `superAdministratorIsNeverTreatedAsTrial`、`TrialOrderPrivacyTest.superAdminSeesRealValues`
  改用超管真实权限集合。
- 关键源码：`TrialAdminGuardInterceptor.java`、`TrialAdminAccess.java`、`TrialIdentities.java`（未改，权威实现）

### 2. 类级注解先抛 → 展厅读券 500

Sa-Token 对类级与方法级注解**都会检查、类级先失败即抛**（反编译 `SaCheckPermissionHandler`
确认：`orRole` 失败同样抛 `NotPermissionException`，方法级注解没有机会执行）。因此上轮
"方法级加 orRole"的修法不生效。

- 修：`DiscountCouponController` 类级改
  `@SaCheckPermission(value={"coupon:manage", AdminPermissions.ADMIN_TRIAL}, mode=SaMode.OR, type="admin")`；
  写接口由 `TrialAdminAccess` 拒绝清单兜底（save/updateStatus/warmup/reconcile 四条都在清单，
  `check_admin_authz.py` 门禁继续强制）。
- 关键源码：`DiscountCouponController.java`、`AdminPermissions.java`

### 3. 异常映射缺口（客户端错误一律表现成"服务器返回错误"）

- `NotLoginException` → HTTP 401 + `code 901`（管理端前端双认，跳登录页）
- `NotPermissionException`/`NotRoleException` → HTTP 403 + `code 403`（与守卫拒绝响应一致）
- `ConstraintViolationException` → `code 600` + 字段级 `data`（用户端登录少传 email 此前 500）
- `HttpRequestMethodNotSupportedException` → HTTP 405 + `code 405`（新增枚举 `CODE_405`）
- 关键源码：`AGlobalExceptionHandlerController.java`、`ResponseCodeEnum.java`

### 4. 登录锁定不让 Redis 抖动阻断登录

`UserLoginLockService` 的 check/recordFailure/clearFailures 包裹 `RuntimeException`：Redis
不可用时降级放行 + WARN（锁定是防爆破加固，可用性优先）。本地日志实证过一次 Redis 连接
重置把登录打成 500。

### 5. 部署可见性与产物一致性门禁（runtime.py）

- `start_app` 区分复用/重启：`already runs the current build (sha, PID); reuse.` /
  `restarting (build old -> new / env changed / command changed).`
- `apps_up` 末尾 `assert_current_build`：每个运行中服务的产物指纹必须等于当前构建产物，
  否则部署失败——"部署没换掉某个服务的产物"不再静默通过
- `apps_status` 输出进程启动时刻与 build 指纹（核对"进程是否启于本次部署"）
- `process_identity` 新增 `expect` 修 fork/exec 窗口竞态（窗口内读到父进程 python 的 argv，
  "稳定但错误"；本地 up 实测 admin 误报，既有缺陷）
- `self_test` 的启动顺序模拟同步豁免新断言（该模拟台账为空，一致性断言语义不适用）

## 部署与部署后复核

**部署后核对（`scripts/probes/post_deploy_check.sh`，22:58 CST）发现关键缺口：**

| 探测（同一 gallery 会话，每条 ×8） | 结果 | 判读 |
| --- | --- | --- |
| `user/loadUser`、`user/changeStatus` | 403 与 200 交替 ★ | user 服务多实例（node1 新 / node2,3 旧） |
| `order/delivery`、`productInfo/updateSkuStock` | 403 与 600 交替 ★ | order / product 服务同因 |

| 未登录基线、缺参、双演示账号登录 | 全部期望 ✓ | — |

**根因**：生产的 `deploy` 动词只更新 **node1（本机）**；node2/node3 的副本服务
（gateway/user/product/order/cart，见 Nacos 注册拓扑）的 JAR 需要
`deploy/cluster/scripts/sync-app-node.sh` 同步——**自集群搭建以来从未执行过应用同步**，
副本节点一直跑搭建时的版本。这解释了本日全部反常现象：

- 展厅账号越权请求约 2/3 概率落到旧副本节点（无 `TrialAdminGuardInterceptor`）被放行；
- "演示买家被禁用"即一次命中旧节点的越权 `changeStatus`（已恢复）；
- 复核里"order/delivery 有时 403 有时 600""user/loadUser 200 而 changeStatus 403"——
  单次探测命中的节点不同，此前"user 服务特例"的判断由此推翻；
- 2026-10-15 的"三机终态"只验证了**服务健康（全 200）**、没有验证**代码版本**，
  所以该缺口一直未暴露（只验健康不验版本，与单机部署事故同一类教训，在节点维度重演）。

**已完成的修复**：

- `deploy/cluster/scripts/sync-app-node.sh`：补"重启 unit + 等健康 + `apps-check`"——
  原脚本只同步 JAR 不重启（"同步了但不生效"是同一个坑的一半）
- `scripts/probes/post_deploy_check.sh`：展厅矩阵每条 ×8 + 一致性判定（本缺口检测工具化）；

- README「运维与排查入口」：新增"副本节点版本"与"部署后核对"两行 + "部署覆盖面（三节点）"
  操作段（含 node1 上执行同步的准确命令）
