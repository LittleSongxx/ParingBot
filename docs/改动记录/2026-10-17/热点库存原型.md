# 热点库存原型（默认关闭）

## 需求

为热点 SKU 保留一条可验证的演进路线：Redis/Lua 预占 → DB 条件更新；默认关闭、只对配置 SKU 生效、DB 始终是事实源。不做纯 Redis 扣减，也不把原型当成生产高并发方案。

## 变更

- 新增 `HotStockProperties`（`smartlect.stock.hot-path`）：`enabled=false`、`skus=productId:hash,...`、`buckets=4`、`reservation-ttl-seconds=900`；可由 `SMARTLECT_HOT_STOCK_*` 覆盖。
- 新增 `HotSkuStockGate`：
  - 首次访问按 DB 库存把可售量拆到 N 个桶（`smartlect:stock:hot:<sku-token>:bucket:i`），ready 标记只初始化一次。
  - `hot_stock_reserve_v1.lua` 原子检查桶总量并按顺序扣减，写 `reservation:<orderKey>`（TTL）；同一订单重复预占返回原数量；库存不足整单拒绝，不留部分扣减。
  - DB 条件更新成功 → `commit` 只删 reservation（桶扣减保留，表示已卖出）；DB 失败 → `release` 回补桶；关单 → 优先 release，标记已过期时按数量回补；退款 → 已初始化时回补。
  - Redis 异常 fail-open 回退 DB 条件更新，指标记 `fallback`；DB 的 `stock + delta >= 0` 仍是最终防超卖。
- 接入 `SkuStockService`：`changeStockBatch` 在 claim 业务键后预占、DB 成功提交/失败释放；`restoreOrderStock` 在事务提交后关单回补；`restoreRefundStock` 提交后回补；`setStock`/单条 `changeStock` 提交后按 DB 重建（有活跃预占时跳过）。
- 新增 `HotSkuStockReconcileTask`（`@XxlJob("hotStockReconcile")`）：无活跃 reservation 时比较桶总和与 DB，差异写 `smartlect_stock_hot_reconcile_diff_total` 并按 DB 重建；有活跃预占不覆盖。
- 指标：`smartlect_stock_hot_reserve_total{result=reserved|insufficient|fallback}`、`smartlect_stock_hot_reconcile_diff_total`。

## 基准

本地单机 10/20 VU、30 秒、全链加购→下单→支付，0 业务错误：

| 轮次 | VU | QPS | p95 | p99 |
|---|---:|---:|---:|---:|
| 关 | 10 | 13.10 | 67.60 ms | 119.51 ms |
| 关 | 20 | 24.83 | 57.27 ms | 186.08 ms |
| 开 | 10 | 13.05 | 60.91 ms | 146.00 ms |
| 开 | 20 | 24.94 | 61.85 ms | 183.16 ms |

20 VU 热点库存轮结束总库存 19728（初始 40×500=20000，272 单），库存守恒。差异在噪声范围内，**不能据此宣称吞吐提升**；这是低并发正确性/回归证据。方法与原始 JSON：`docs/verification/order-load.md`、`eval/verification/2026-10-17/order-load/`。

## 未完成/边界

- 默认关闭，未在生产/真实大促开启；桶不跨节点分片，单 Redis。
- 桶与 DB 的一致性靠对账；管理端直接改库存或 Redis 故障恢复后，存在短暂少卖/多卖的窗口，DB 条件更新仍防负库存。
- 退款回补是 best-effort；Redis 失败由对账兜底，不是强一致。
- 没有做多仓/共享库存/跨区域单元化。
