08 · 支付与 Outbox

支付是模拟的，但一致性是真的：pay 库一个事务里「改状态 + 落 Outbox」，事务提交后异步投 RocketMQ；order 消费端三层幂等。支付成功这件事，最终一定被订单知道。

支付成功事件流

Outbox：本地消息表的生与死

要点

  • 为什么 Outbox 而不是事务消息：业务事实（支付单 0→1）和「要发的消息」在同一个本地事务里原子落库——不存在「库改了消息没发」或反过来。
  • 金额不信任入参：收银台地址、金额一律以 pay_trade_record 为准；expectedAmountCents 不符直接 409 要求重新确认。
  • 拒绝 ≠ 关闭：mock decline 只向 pay_payment_attempt 插一条 DECLINED 事实，支付单状态不动——「试了没成」和「单子关了」是两回事。
  • 退款幂等：SELECT … FOR UPDATE 串行化 + pay_mock_refund 台账按退款单号重放 + 累计 ≤ pay_amount。
🧺 案例进度 shopper 在模拟收银台点「支付 ¥8994」：pay_trade_record 0→1 → Outbox → RocketMQ → order 收到：订单 WAIT_PAYMENT → PAID，券标记已用，明细的 paid_amount 分摊落账，1 小时后物流自动推进。若 shopper 15 分钟都没付钱？下一章。
