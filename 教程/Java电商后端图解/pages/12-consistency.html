商Smartlect 图解

12 · 一致性总纲

把前面 11 章的机制叠起来看：一套五层防线，代替了分布式事务框架。每层只回答一个问题——「上一层没拦住的，我来拦」。

为什么敢移除 Seata

  • ADR-0006 决策：移除 Seata 全套（server / undo_log / pom / yml / 注解），移除前对秒杀补偿链做了自洽核验。docs/adr/0006-remove-seata.md
  • 现状可验证：全库 0 个 @GlobalTransactional、0 个 seata 依赖；残留只有 file.conf 历史文件和两处注释。
  • 取舍：XA/AT 换来的是「写路径的全局原子」，代价是运行时组件、锁持有时间、排障复杂度；而这个项目的写流量是单店规模——用幂等 + 补偿换简单性，更划算。

场景 × 防线对照

场景用到的层关键证据
下单L1 + L2 + L3幂等账本 / validateAndLock / order-deduct 键 / Outbox 关单消息
支付成功L2 + L3pay_trade_record 0→1 条件更新 / Outbox pay-success / 消费三层幂等
超时关单L415min 定时消息 → PAYMENT_TIMEOUT → 回补库存 + 券解锁
秒杀抢券L1 + L2 + L5限流 + Lua 三键 / DB remain_count>0 / 10min 对账重灌
退款L1 + L2 + L4 + L5稳定退款单号 / 明细 refunded_amount 累加 / 30s Saga 续推
商品搜索—（降级）ES 挂 → LIKE；同步链路挂不影响查询
💡 一句话总结 Smartlect 的交易一致性 = 「每一步都敢重做」：请求可重放（幂等键）、资源更新带条件（CAS）、消息必达（Outbox）、时间会触发（定时消息）、最后有人对账（xxl-job）。五件小事叠起来，替代了一件大而脆的事（分布式事务）。代价是：读代码时脑子里要装五个机制，而不是一个 @GlobalTransactional。
