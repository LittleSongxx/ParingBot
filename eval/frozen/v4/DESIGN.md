# v4 评测集设计（P1）

> 状态：**设计稿已生成并冻结场景，标签待人工/judge**；尚未替换 v3 门禁。
> 目标：把“8 个正向场景、单 trial”的 v3 扩成能支撑**分层结论、稳定性、对照**的评测集。

## 1. 规模与分层

| 项 | v3 | v4（本设计） |
|---|---|---|
| 正向场景 | 8 | **40** |
| 负向/异常场景 | 2 | **8**（4 缺动态 + 4 缺自我介绍） |
| trials | 1 | **3（运行协议，不在场景文件里）** |
| 容量层 | 高 3 / 中 3 / 低 2 | **高 16 / 中 12 / 低 12** |
| 性别 | 4/4 | 目标 20/20，实际 19/21（16 门店、5 租期档） |

## 2. 构造规则

- 场景来自种子数据 `deploy/mysql/sql/base/01-paringbot.sql` 的 900 名成员；
- 每个场景是“门店 × 性别 × 租期档”格，容量 = `approved_candidates + 同性 + 租期档差<2 + 双向必须项`；
- 分层抽样：高容量（≥8）、中（4–7）、低（1–3），配额 16/12/12；
- 必须项计划：高容量 年龄+作息；中容量 交替加门店/预算；低容量 交替加预算/宠物；
- 确定性：`seed=20261104`，`python eval/build_v4_scenarios.py` 可字节复现；
- 负向：从正向场景复制档案，分别清空 `moments` / `self_intro`，`run=false`，记录预期 blocker。

详见 `COVERAGE.md`。

## 4. 标签（P1 关键待办）

- **不使用 heuristic gold**；v4 的标签必须来自人工或经校准的 judge：
  - 每个正向场景交付 8 人 + 8 个对照（随机/难负例）；
  - 相关性分级 0–3（0=硬冲突，1=勉强，2=合适，3=非常合适）；
  - 报告 precision/recall/win rate，而不是只用“交付数”；
- 在标签完成前，v4 只用于**流程/成本/稳定性**试点，不能作为质量门禁。

## 5. 运行协议

- 先做 **12 个场景 ×3 trials** 的方法验证（成本约 1/4），确认 pass^k 与 CI 可用；
- 再全量 40×3（当前 8 场景 1 trial ≈1.66M token，粗算约 25M token）；
- 每次运行记录 MANIFEST hash、模型配置、artifact；
- 对照候选不进入生产供给，不写 eval profile。

## 6. 验收标准

1. `python eval/build_v4_scenarios.py --check` 通过：40+8、无重复格、容量≥1；
2. 场景/标签/运行脚本哈希冻结，CI 可复现；
3. 12 场景×3 trials 产出 pass^k/CI，且与 v3 结论不冲突；
4. 人工/judge 标签完成 ≥100 对，报告 κ（人工）与 judge 校准；
5. 此后才允许把 v4 接入门禁。

## 7. 明确不做

- 不按结果补供给；
- 不用 heuristic 标签伪装成 v4 gold；
- 不在 v4 标签完成前对外声称“质量提升”。
