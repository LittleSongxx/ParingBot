先记住这条根约束

一次下单，至少要动五个地方：订单库、库存库、券库、支付库，还要读用户地址。这些数据分属不同服务、不同 schema，仓库里没有 Seata、没有 XA，也没有一个能包住五者的本地事务。

所以整个后端的设计都围绕一句话展开：用本地事务保住"自己库里的那一条事实"，用幂等、Outbox、补偿和状态机把跨服务的结果慢慢收敛。后面的每个机制，都是这句话的某种展开。

✦ 读代码时抓住三条线

数据真相线：价格与库存谁是权威？缓存里存了什么、不存什么？

状态线：谁有资格改状态？改状态时带了什么前置条件？失败后停在哪个可恢复的点？

Part I · 全景

01九服务一张图：谁在读，谁在写

为什么刻意不引入 Seata

仓库在早期做过 Seata 试验，后来移除了。原因并不神秘：跨五个库的全局事务会把所有服务绑在同一个协调者上，连接占用、故障面和运维复杂度都会上升。当前选择是本地事务 + 最终一致：

  • 本地事务只保自己库里的订单、库存、支付单、券状态；
  • Outbox 把"业务落库"和"消息产生"绑在同一个本地事务里；
  • 幂等键挡住重复请求、重复投递、重复扣减；
  • 补偿与对账把失败、超时、丢失的事件慢慢拉回正确状态。

这套组合的代价是"中间态"一定存在：订单可能已支付但券还没核销，退款单可能已通过但库存还没回补。读代码时不要把这些中间态当成 bug，它们是设计的一部分；关键是每个中间态都有下一步能收敛。

ⓘ 一个容易混淆的边界

商品不存库存，缓存也不存库存。商品服务只保存 SKU 的规格与价格；库存数量在 sku_stock，由库存服务裁决。商品详情缓存里即使有 stock 字段，也会在写入缓存前清零，读取时再实时回填。这条边界会在第 05、06、11 章反复出现。

自测：不看图，说出一次下单会写哪些库？为什么网关不能替服务做权限判断？

下单至少写订单库、库存库、券库、支付库，并写各自的 Outbox；地址是读。网关只能看到 token 对应的会话键是否存在，它不知道这个用户是不是订单的归属者、有没有某个权限点，也不知道商品是否上架，所以业务鉴权必须在服务端。

ⓘ 端口与启动

application.yml 的默认端口是 18080–18088；本地 scripts/runtime.py 会用环境变量覆盖成 18101–18108，避免和已占用端口冲突。基础设施用 deploy/compose.yaml 起，Java 服务以可执行 JAR 方式在宿主机启动，不容器化。

一个请求会穿过哪些层

  1. Controller

    只做参数校验、取会话身份、调用 biz；不写 SQL，不拼业务事务。

  2. biz / 编排服务

    真正的用例：下单、锁券、扣库存、状态迁移。跨服务调用通过 *RpcSupport，而不是直接 HTTP。

  3. Mapper / 本地事务

    每个服务只操作自己的 schema；跨库一致性交给幂等、Outbox、补偿。

  4. Dubbo / internal HTTP

    provider 和 consumer 共用同一业务层；内部接口用 X-Internal-Token 保护，公网网关不映射 /internal/**。

自测：如果 order 想新增一个"查询用户昵称"的能力，应该改哪里？

先在 user 的 api 里加 DTO/VO 与 Dubbo 方法（或复用已有 UserRpcSupport 方法），在 user 的 app 里实现，再在 order 的 app 里通过 UserRpcSupport 调用。不要让 order 直接查 smartlect_user 库，也不要把 user 的 Mapper 依赖进 order。

网关的五个细节

  1. 先剥头，再判断

    AuthGlobalFilter 一进来就删掉 X-User-Id、X-Internal-Token、X-Admin-*、X-Trace-Id 等客户端可伪造的头。它不信任任何"我已经登录"的自述。

  2. 用户端读值，管理端查键

    用户端 token 对应 token:login:token:{token} 的 loginId；管理端有独立 realm，键是 adminToken:admin:token:{token}，网关只做 hasKey。

  3. 不注入身份头

    历史上曾有 X-User-Id 之类的头，现在已经没有任何消费者。服务端统一从 Sa-Token 会话取 userInfo，避免"网关注入什么、下游就信什么"的隐式契约。

  4. 白名单是整前缀

    /api/product/** 整段免登录，因为商品浏览是公开的。这也意味着新增写接口不能放在这个前缀下，否则会静默变成免鉴权接口——第 22 章会把这个坑单独列出来。

  5. 内部路由不存在

    网关没有 /internal/** 路由；内部调用走本机直连或 Dubbo。但 InternalTokenGlobalFilter 仍然保留，作为"以后有人加路由"时的安全网，缺令牌一律拒绝。

Trace 怎么贯穿

网关的 TraceIdGlobalFilter 优先级最高：优先接受合法的 W3C traceparent，其次接受 16–32 位小写 hex 的 X-Trace-Id，都没有就生成 32 位 hex。它写入 MDC 与响应头。下游 TraceIdFilter 再做同样的恢复；Dubbo 通过 attachment 透传，RocketMQ 把 traceId 写进消息属性，线程池用 MdcTaskDecorator 传递。

一个容易忽略的细节：网关的 Trace 过滤器在 Auth 之前执行，而 Auth 又会剥掉客户端传来的 X-Trace-Id。如果没有合法的 traceparent，网关新生成的 traceId 可能到不了下游——读链路时可以用一次请求实际验证。

自测：为什么网关不能直接相信 X-User-Id？

因为任何客户端都能自己加这个头。网关必须先剥掉它，服务端再用会话里的 loginId 反查身份；否则攻击者只要写一个 X-User-Id 就能冒充别人。内部服务之间的 X-Internal-Token 同理，必须常量时间比较且未配置即拒绝。

Part I · 骨架

04双身份与三层防线：前端隐藏不等于权限

Smartlect 有两套完全独立的登录体系：用户端 StpUtil 与管理端 StpAdminLogic。它们不共享 token、不共享会话、不共享权限模型。把这两套身份分开，是后面所有权限判断的前提。

两套 realm

用户端 · StpUtil

tokenName=token，有效期 86400 秒，允许并发登录、不共享 token。登录后 session 里放 userInfo；网关读 token:login:token:{token} 的 loginId。

账号在 user_info，密码 BCrypt

管理端 · StpAdminLogic

loginType=admin，tokenName=adminToken，有效期 86400 秒，不允许并发登录。session 里放 adminPrincipal；网关只对 adminToken:admin:token:* 做 hasKey。

账号在 admin_account，角色/权限点独立

登录时发生了什么

  1. 先看锁定

    UserLoginLockService 以 email + IP 为键，5 次失败锁 15 分钟；Redis 故障时放行，避免登录整体不可用。

  2. 再过验证码

    SlideCaptchaVerifier 校验滑动拼图；演示账号跳过。验证码 token 与结果都在 Redis，成功/失败都会清理。

  3. 校验密码

    PasswordService 使用 BCrypt cost=10，兼容旧 MD5 并在登录时升级。密码字段 @JsonIgnore，不会随用户信息返回。

  4. 检查状态

    禁用、临时封禁都会在登录时拒绝；封禁以 DB 的 temp_ban_until_ms 为事实源，Redis 只是缓存。

  5. 建立会话

    StpUtil.login 后把 userInfo 写入 session，更新最后登录时间/IP。改密会 cleanAllToken，让旧 token 全部失效。

管理端 RBAC

管理端不是"用户表加一个 is_admin 字段"，而是独立的一套表：admin_account、admin_role、admin_permission、admin_account_role、admin_role_permission。登录时 AdminIdentityService 聚合角色与权限点，写进 AdminPrincipalDTO，再由 SmartlectStpInterface 提供给 @SaCheckPermission(type="admin")。

角色或状态变更会提升 session_version 并让旧会话失效，避免"改了角色但对方还拿着旧权限"。高危写操作还会要求 X-Admin-Confirm-Pwd 二次确认，由 @AdminSensitiveConfirm 切面校验操作者口令。

试用身份为什么要在服务层再挡一次

展厅账号是公开的，任何人都能登录。只靠前端隐藏按钮没有意义；只靠网关也不行，因为网关不知道"visitor 不能下单"。所以服务端有三层：

  • 过滤器：TrialUserWriteFilter 读 token 会话，命中 visitor 后对写路径直接返回 403 JSON。
  • 拦截器：TrialAdminGuardInterceptor 对 /admin/** 的展厅账号拒绝隐私面与写接口，只放行退款复核、登出等白名单。
  • 服务层：改密、改资料、注册、地址归属等再判一次，防止有人绕过 Controller 直接调内部接口。
✗ 三个常见误判

① 持 admin:trial 权限点就是展厅？ 不是。展厅身份按账号/角色判定，超管即便持有全部权限点也豁免。
② visitor 和 shopper 是同一种试用？ 不是。isTrialUser 只认 visitor；shopper 是另一套限制，服务层单独挡资料与改密。
③ 前端隐藏了按钮就安全？ 不是。任何权限都必须能在服务端找到拒绝点；找不到就是漏洞。

用户域还有什么：地址、验证码、审核与封禁

用户服务不只登录。它还要处理地址归属、滑动验证码、邮箱验证码、头像审核与临时封禁；这些能力共同决定"这个账号现在能不能做什么"。

06商品读链路与搜索同步：三条路，各自负责什么

商品详情、商品列表、关键词搜索看起来都是"查商品"，其实走的是三条不同的路：详情走多级缓存，列表走 SQL 分页，搜索先用 ES 过滤再回库。把三条路混成一条，就会在缓存、索引和一致性的细节上反复踩坑。

详情读：缓存里为什么要把库存清零

ProductInfoServiceImpl#getProduct4VOByProductId 的读顺序是：布隆过滤器 → L1 Caffeine → L2 Redis → MySQL。缓存里存的是商品静态信息（SPU、属性、SKU 价格），所有 SKU 的 stock 在写入缓存前被清零。命中缓存后，再用 StockRpcSupport#getAvailableBatch 实时补库存。

这样做的原因很直接：缓存 TTL 是 300 秒，库存却可能每秒都在变。如果缓存里保留库存，用户会看到 5 分钟前的旧值，下单时再被库存服务拒绝，体验和一致性都很差。把库存从缓存里拿掉，缓存只负责"商品长什么样"，库存服务负责"现在有没有货"。

  • 没有空值缓存：缓存 miss 后查库，查不到不写 null；布隆过滤器说"不存在"后仍会回查 DB 一次，所以它只降低部分穿透，不是严格防线。
  • L1 失效靠广播：失效时删 L2 并向 smartlect:product:invalidate 发消息，所有实例清本地 L1；广播失败时其他实例靠 60 秒 TTL 收敛。
  • 缓存返回副本：copyOf 深拷贝 SKU 列表，避免调用方补库存时污染 L1 里的快照。

列表：分页、排序与分类

列表接口 POST /product/loadProduct 用 PageHelper 物理分页。单页上限 100、页码上限 500，防止深分页把数据库拖垮。排序只允许 COMPOSITE / PRICE / SALE 三种，通过 SafeSort 拼进 order by；客户端不能直接传 orderBy，QueryBindingControllerAdvice 会拒绝。

分类查询同时匹配 category_id 与 p_category_id，用 UNION 去重；价格筛选只比较 min_price。这些细节决定"分类页看起来对不对"，读代码时建议拿一个二级分类实际跑一次 SQL。

搜索：ES 只做文本过滤

索引名硬编码为 smartlect-products。映射里 productName 是 text(zh_text) + .raw keyword，productDesc 是 text，另有品牌、分类、状态、销量、推荐、目录范围等字段。默认 smartlect.search.mode=substring，谓词是 productName.raw 的大小写不敏感 wildcard，语义与 SQL LIKE 一致；只有 hybrid 模式才叠加分词 match。

查询同时过滤 status=1、排除 catalogScope=eval、排除指定 ID，按创建时间倒序，最多返回 500 个 ID。Controller 拿到 ID 后再回 MySQL 做分类、价格、排序和分页。所以 ES 不是"完整搜索服务"，它只负责文本召回。

✗ 三个真实存在的搜索边界

① ES 返回空列表时，Controller 只判 null 不判空：空列表传给 Mapper 后 <if size>0> 不生效，关键词零命中会退化成"返回全部在售商品"。ProductCommerceInternalController.searchOnSale 对空结果显式返回空，是正确的写法。
② 全量重建会被分页上限截断：rebuildAll(500) 内部走 PageUtils，单页被压到 100，随后判断 page.size() < pageSize 直接 break，默认只重建第一批 100 条。
③ 索引写失败可能被吞掉：upsert/delete 只捕获 IOException 并返回 false，消费者没有检查返回值；连接类失败可能只留日志，直到下次重建。

索引同步：Canal → RocketMQ → Consumer

Canal 以 serverMode=rocketMQ、flat JSON 直投 smartlect-canal，只订阅 smartlect_product.*。消费者只处理 product_info 表：DELETE 删索引，其余按行 upsert，然后对涉及的 productId 统一失效详情缓存。消费组只有一个，依赖单组保序与幂等 upsert；idempotencyTtlSeconds=0，不走 Redis 幂等租约。

启动时的 ProductIndexInitializer 用后台线程检查 ES 文档数：如果少于在售商品数，或强制重建，就调用 rebuildAll(500)。ES 不可达时跳过，不阻塞健康检查。

自测：为什么商品详情命中缓存后还要调用库存服务？

因为缓存里存的是静态快照，库存被清零；库存变化频率远高于商品文案，且库存是交易事实，不能接受 300 秒的陈旧。详情每次命中都用 getAvailableBatch 取实时库存，保证页面展示与下单校验使用同一份事实。

锁券：一次条件更新

CouponInternalService#validateAndLock 先做校验：券存在、属于当前用户、状态是 NOUSE、模板存在、在有效期内、满足门槛；然后算折扣，并用 capCouponDiscountForMinPay 保证实付不低于 0.01。最后执行一次条件更新：

UPDATE user_coupon SET status = CANT
WHERE user_coupon_id = ? AND user_id = ? AND status = NOUSE

影响行数不等于 1，就说明券已经被别人锁了，直接抛"优惠券已被使用"。没有 LOCKED 状态、没有 version 字段，锁与解锁都靠状态 CAS。下单失败时，订单服务把 CANT 改回 NOUSE；支付成功时改成 USED。

秒杀券：Redis 是闸门，DB 才是账本

秒杀链路常被误读成"Redis 预扣 + MQ 异步落库"。实际是：Redis Lua 先做预扣，随后同步调用券服务扣 DB 库存，再在订单短事务里写订单与 15 分钟超时消息，最后创建一张 CANT 占位券；MQ 只负责超时兜底。Lua 同时改三个键：

  • smartlect:rushing:stock:{couponId}：剩余库存；
  • smartlect:rushing:coupon:{couponId}：参与者 SET，用于清理僵尸成员；
  • smartlect:rushing:userId:{uid}:coupon:{cid}：用户预占 hash，TTL 900 秒，防重复领取。

Redis 返回 0 成功 / 1 无库存 / 2 重复。DB 侧用 remain_count 条件更新防超发；任何回补最终都用 DB 的余量对齐 Redis，CouponRushReconcileTask 每 10 分钟做一次对账。支付成功后占位券从 CANT 激活为 NOUSE；超时未支付由死信监听分四种形态回滚库存。

券缓存与管理端

券详情缓存 key 是 smartlect:coupon:detail:{id}；广场列表用版本号 smartlect:coupon:plaza:version 做整体失效，逻辑 TTL 30 分钟、物理 TTL 24 小时、空值 2 分钟。写后删详情并递增版本，避免逐页删除。

管理端 /admin/discountCoupon 有 6 个接口：保存、列表、详情、改状态、预热秒杀库存、对账。类级权限是 coupon:manage 或 admin:trial，展厅账号还会被 TrialAdminAccess 拒绝写接口，改状态需要二次口令确认。管理端没有"发券"接口，发券走内部 grantCoupon。

✗ 五个容易误读的券细节

① 锁券不是核销：CANT 只是锁定；支付成功才 USED。
② CANT 不是单一语义：订单锁、秒杀占位、已作废都用它；读代码要结合调用方。
③ 模板停用不一定挡得住：validateCoupon 只看有效期，不检查模板 status；停用券仍可能被使用。
④ 部分退款不退券：只有整单全退且没有剩余 NORMAL 明细时才发退券消息。
⑤ coupon_scope 不参与结算：结算与锁券都不校验适用范围，别把它当成硬约束。

自测：为什么取消订单只把 CANT 改回 NOUSE，而不是删掉用户券？

因为用户券是用户资产，取消订单只应释放"这笔订单对券的占用"，券本身仍然属于用户，且可能还在有效期内。把它退回 NOUSE 后可以再次使用；只有过期或作废才进入终态。删券会造成用户资产丢失，也无法审计。

09下单五阶段：本地事务只包住第三段

下单是整个后端最值得逐行读的用例。它没有把"锁券、扣库存、建支付单"包进一个大事务，而是拆成五段：读准备 → 锁远程资源 → 短本地事务 → 事务外远程写 → 失败补偿。理解这个拆分，就理解了 Smartlect 的一致性策略。

阶段一：读准备（不占连接）

prepareOrder 做的是"把一次下单需要的事实读齐"：校验支付方式与下单来源，查收货地址，调用商品快照，校验 SKU 存在、商品在售、限购数量，再调用库存服务做一次可用量预检。然后按 productId 聚合成多张 OrderInfo，按规格生成 OrderItem，生成 orderId 与统一的 payOrderId，初始状态都是 WAIT_PAYMENT。

这里有一个容易忽略的设计：一笔支付单可以对应多张子订单。购物车里有两件不同商品时，会生成两张 order_info，共享同一个 payOrderId；券关系只挂在第一张子单上。后面的支付成功、退款、关单都按 payOrderId 聚合处理。

阶段二：锁远程资源

有券时调用 couponRpcSupport.validateAndLock，把用户券从 NOUSE 改成 CANT。拿到折扣后，按 orderId 排序逐单冲减，再用 ensureOrderListMinTotalPay 保证总实付不低于 0.01。锁券发生在本地事务之外，因为它是另一个服务的本地事务；失败时还没有写订单，直接抛错即可。

阶段三：短本地事务

只有这一段用 TransactionTemplate 包住，且只做数据库写入：插券关系、订单、明细、物流，把下单幂等键盖到每张子单上，并为每张子单写一条 15 分钟超时关单的 Outbox 消息。订单落库与"关单消息会产生"在同一个本地事务里，避免出现"既没有支付意图、也没有人会来关单"的永久孤儿订单。

✦ 为什么不在方法上加 @Transactional？

因为方法里有商品、券、库存、支付等远程调用。远程调用期间如果一直占着数据库连接，连接池会被抽干——代码注释里记录了压测时 18.1 秒的连接占用。把远程调用移到事务外，本地事务缩到毫秒级，是这套编排最重要的性能决策。

阶段四：事务外远程写

P3 提交后，订单已经真实存在，接下来按顺序做四件事：

  1. 扣库存

    changeStockBatch 传负数，业务键 order-deduct:{payOrderId}；库存服务先用 INSERT IGNORE 写账本，再逐 SKU 条件更新。

  2. 清购物车

    只有 orderFrom=CART 才调用 deleteBatch，删除已购行；不是清空整个购物车。

  3. 建支付单

    createPending 写 pay_trade_record，唯一键 pay_order_id；重复创建只接受同用户、同订单、同金额。

  4. 取支付表单

    getPayUrl 是 best effort：失败不阻塞下单，用户可以稍后从订单页继续支付。

阶段五：失败补偿

P4 任何一步抛异常，进入补偿：库存已扣则调 restoreOrderStock（幂等），券已锁则把 CANT 改回 NOUSE；补偿本身失败，写入 RemoteCompensateRecorder，由补偿任务重放。订单不会因为 P4 失败而回滚——它已经落库，并带着 15 分钟关单消息，最终会被关闭。

V2 报价：先 claim，再建单

quoteOrder 只做报价，不锁券、不写订单；createConfirmed 先用 orderQuoteService.claim 在短事务里占用报价，再执行建单副作用。claim-first 的作用是：并发重复请求在占用处就被 409 挡下，不会先落单后才发现冲突，留下孤儿订单。报价表 order_quote 对 pay_order_id 有唯一键，金额以分为单位，并带过期时间。

✗ 读下单代码时的四个误判

① "下单是一个事务"：不是，只有 P3 是。
② "P4 失败订单就没了"：订单仍在，状态待付款，最终由超时消息关闭。
③ "券和库存会跟着订单回滚"：不会，靠 P5 补偿与幂等回补。
④ "支付单和订单是一对一"：一个 payOrderId 可对应多张子订单。

自测：为什么超时关单消息要和订单写在同一个本地事务里？

因为 P4 可能失败，订单已经落库但没有支付意图。如果关单消息没写进去，这张待付款单就永远不会被关闭。把订单行与 Outbox 消息放在同一个本地事务里，保证"订单存在 ⇒ 至少有一个关单消息会投递"，把孤儿订单收敛掉。

✗ 三个常见误解

① "幂等就是只执行一次"：不是。它可能执行了，但第二次请求不会产生新的业务副作用，并返回第一次的结果。
② "有幂等键就不会重复下单"：键由客户端生成；客户端每次重试都换新键，账本也挡不住。键必须稳定复用。
③ "FAILED 可以重试成 SUCCESS"：FAILED 是确定性结果；要重新下单，必须换一个新的键，并明确这是一次新的业务请求。

自测：为什么 COMPLETED 不能像 PROCESSING 一样用 REQUIRES_NEW？

为什么不是"先查再改"

先 SELECT stock 再判断、再 UPDATE，在并发下会出现两个请求都读到 1、都认为够、都去扣的竞态。即使把 SELECT 放进事务，也要显式加锁或提高隔离级别，代价更大。当前写法把判断放进 WHERE：

UPDATE sku_stock
SET stock = stock + #{changeAmount}
WHERE product_id = #{productId}
  AND property_value_id_hash = #{propertyValueIdHash}
  AND stock + #{changeAmount} >= 0

当 changeAmount 为负数时，条件等价于 stock >= -changeAmount。数据库在行锁内完成"读当前值 → 判断 → 写新值"，影响行数为 0 就代表库存不足。批量扣减会先按 SKU 合并数量、按 key 排序，再逐条更新；任一失败抛异常，整个本地事务回滚。

① "影响 0 行一定是库存不足"：也可能是幂等账本已处理，或 SKU 不存在；调用方要结合上下文解释。
② "回补就是 stock += n"：回补前要确认扣减发生过，否则会把没扣过的订单加出幽灵库存。
③ "库存服务有悲观锁"：没有实际的 select ... for update 调用；靠的是 UPDATE 的行锁与账本。

自测：为什么扣减账本要在改库存之前插入？

CAS 更新与 0 行

transition 把目标状态写进更新对象，把期望状态放进查询条件，然后调用 updateByParam，返回影响行数。若期望状态就是目标状态且没有额外 patch，它会退化成一次读比对，避免无谓 UPDATE。transitionPayOrder 按 payOrderId 做批量 CAS，用于支付生命周期。

  • 当前状态不允许这个事件；
  • 订单不存在，或 payOrderId 下没有符合条件的子单。

✗ 读状态机时的四个误判

① "0 行就是失败"：可能是并发者已成功，或本来就处于目标状态。
② "CLOSED 和 CANCELLED 一样"：前者是系统关闭/超时，后者是用户主动取消；后续补偿与文案不同。
③ "订单状态就是支付状态"：不是。支付单有自己的 trade_status（待支付/成功/关闭/退款），订单状态是业务视角。
④ "明细状态跟订单状态一起变"：明细只有 REFUND / NORMAL；部分退款时订单变 PARTIALLY_REFUNDED，明细按行置 REFUND。

自测：为什么状态机不直接用 UPDATE ... WHERE order_id = ?？

因为那样会无条件覆盖并发者已经写入的状态。带上旧状态条件后，数据库只会在"当前仍是我读到的状态"时更新；并发者先改，我的影响行数就是 0，从而知道竞争失败。这就是乐观并发控制，不需要额外版本号。

写入：同事务、同键、同载荷

TransactionalMqSender#sendAfterCommit 在业务事务内调用 savePending，把消息行写进 Outbox；事务提交后异步触发 tryDispatch。同键同载荷再次写入会复用已有行；同键不同载荷会抛错，避免"同一个业务键被两条不同消息复用"。

这一步的语义是"业务数据与消息意图同生共死"：订单落库成功，关单消息就一定在 Outbox 里；订单回滚，消息也不会单独留下。

投递：租约、park 与退避

tryDispatch 先用数据库 SQL 抢租约（claimForDispatch），抢到才允许发送；发送成功后 markSent 还要校验租约仍在，防止租约过期后被另一个实例接管造成双投。失败则按指数退避更新 next_retry_time，封顶 5 分钟。

对于 7 天确认收货这类远未来消息，broker 的时间轮有单条最大延迟（默认 24 小时），直接投会被拒绝。Outbox 会先把消息 park 到 delivery_expire_at 进入时间窗，再由 outboxDispatch 每 5 秒扫描重投。正确性靠数据库租约，Redis 锁只用于防抖。

消费：Redis 双标记与补偿

消费者不是直接处理业务，而是先经过 MqConsumerIdempotencyHelper：用 Lua 原子地写 processing 租约，处理成功后写 done 标记。遇到 BUSY 就 30 秒后回投；业务异常按 5s/30s/120s 回投原 topic/tag；重试耗尽写 mq_compensation_log，由 xxl-job 自动重放或管理端手工重放。

因此整条链是 at-least-once：消息可能重复，但消费幂等会把重复挡在业务之外。不要把 Outbox 当成 exactly-once。

✗ 三个常见误读

① "Outbox 是 MQ 事务"：不是。它是本地事务写表 + 提交后投递，中间仍有时间窗。
② "消息只会来一次"：不是。重试、回投、人工重放都可能重复；消费必须幂等。
③ "Redis 锁保证不双投"：不保证。投递正确性主要靠数据库租约；Redis 锁只是降低抖动。

自测：为什么发送成功后还要校验租约？

因为发送可能耗时超过租约期，另一个实例可能已经接管并重投。如果发送成功后无条件 markSent，两个实例都以为自己是唯一投递者，消息就被重复发送。校验租约可以在这个竞争窗口里只允许一个实例落 SENT。

  1. 先验结算

① 支付成功事件与 markSuccess 不在同一事务：所以需要 payOrderPoll 兜底，不能假设事件一定到达。
② mock 没有验签：不要把它当成真实渠道安全模型。
③ 支付单状态 ≠ 订单状态：支付单可能已退款，订单可能仍在退款 Saga 中；反过来，订单已关闭也可能收到迟到支付。

因为关单可能已经回补库存、释放券，甚至商品已被别人买走。把订单"复活"会造成超卖和券状态错乱。正确做法是承认这笔钱已经收了，但交易不再成立，原路退款，并让订单保持关闭状态。

为什么按"明细"退款

refund_request 的唯一键是 order_item_id，不是 order_id。这支持"一张订单里退其中一件商品"：每个明细一条退款记录，累计 refundedAmount，再按剩余 NORMAL 明细数量决定订单变成 PARTIALLY_REFUNDED 还是 REFUNDED。退款号用 orderItemId 生成稳定 UUID，重复提交靠唯一键幂等。

三个阶段

  1. 支付退款

    先 CAS 抢支付租约，避免并发退款；调支付服务退款；成功后状态变 PAYMENT_CONFIRMED。失败按 60 秒、最多 6 次重试，耗尽转人工。

  2. 库存回补

    queueStockRestore 在一个本地事务里翻明细、累计金额、算订单聚合状态、置 STOCK_PENDING，并写 refund-stock Outbox。库存服务用 refundRequestId 做幂等键回补，成功后回发 refund-result。

  3. 退券与收口

    只有整单全退且没有剩余 NORMAL 明细，才写 refund-coupon-return Outbox；券消费端做 USED→NOUSE。库存结果到达后 Saga 置 COMPLETED。

人工复核与对账

支付重试耗尽、库存队列失败或库存重试耗尽，都会把 Saga 推到 MANUAL_REVIEW。管理端退款复核可以 approve 或 reject：approve 按 review_origin_status 恢复到原阶段继续跑，reject 置 REJECTED；用户重新发起时 resetRejected 可以从拒绝态回到原阶段。refundSagaReconcile 定时取到期的退款单续跑，避免只靠一次调用。

✗ 三个退款边界

① 订单已 REFUNDED，库存可能仍在 STOCK_PENDING：订单聚合状态与 Saga 状态不是同一个字段。
② 部分退款不退券：只有整单全退才触发退券；部分退款后券仍视为已使用。
③ 退款不是一次远程调用：支付、库存、券是三段，中间任何一段失败都靠持久化状态与重试收敛。

自测：为什么退款库存回补要用 refundRequestId 做幂等键，而不是订单号？

因为一张订单可以多次部分退款，每次退款是独立的 refund_request。用 refundRequestId 才能区分"第几次退款"，重复消费同一条退款消息不会双加库存；用订单号会把多次退款合并，导致漏加或重复加。

16延迟任务与对账：让中间态自己走完

Smartlect 的很多状态不会在请求里立刻完成：15 分钟后关单、1 小时后推进物流、7 天后确认收货。它们靠延迟消息与定时对账推进。延迟消息负责"准时提醒"，对账负责"错了再拉回来"。

三档延迟消息

✦ 为什么租约与退避都用数据库时间

如果租约用应用服务器时间，多实例时钟漂移可能让一个实例认为租约已过期、另一个认为还没过期，从而双投。Outbox 的 claimForDispatch、parkUntilTimerHorizon、退避时间都用 SQL 的 NOW() 推导，把"谁先谁后"交给同一个数据库时钟。

自测：payOrderPoll 扫描到一笔超过 180 秒仍待支付的订单，它会直接关单吗？

不会。它只查渠道状态：如果渠道显示成功，就补发支付成功；如果没成功，就交给 15 分钟延迟消息与取消服务关单。对账任务不负责关单，避免和延迟消息、用户取消产生多套并行的关闭逻辑。

统一响应与异常

所有 Controller 返回 ResponseVO{status, code, info, data}，成功码 200。异常由 AGlobalExceptionHandlerController 统一分流：参数校验 600 + 字段明细、唯一键 601、未登录 401 + 901、无权限 403、404/405 单独处理，其他 500；同时把 400/401/403/409/410/429 同步到 HTTP 状态码，方便网关和前端判断。

该不该放进 common

用三个问题判断：

  1. 这个能力是否多个服务都需要，且与具体业务实体无关？
  2. 它是否只依赖通用基础设施（Spring、Redis、MQ、Dubbo），而不依赖某个域的 Mapper？
  3. 如果把它删掉，是否每个服务都要重复写一遍？

三个都是"是"，才放进 common。像"订单金额怎么分摊""券能不能叠加"这类规则，属于订单/券域，不能因为"好复用"就搬进 common。

为什么没有跨库外键

外键只能在同一个数据库内生效；跨 schema 建外键会把两个服务的写入绑在一起，破坏"服务只写自己的库"的边界。当前用逻辑关联 + 索引：order_info.pay_order_id、order_item.order_id、refund_request.order_item_id 都有索引/唯一键，但数据库不会替服务保证父行存在。

代价是可能出现"孤儿引用"（例如退款单指向的明细被删）。系统用状态机、幂等账本与对账任务处理这些情况，而不是靠数据库级联。

Flyway 与账号

每个服务的迁移目录是 classpath:db/migration，配置 baseline-on-migrate=true、baseline-version=0、validate-on-migrate=true。运行账号 smartlect_app 只拥有业务库 DML，Flyway 用独立账号；Canal 账号只有 REPLICATION 权限。这样迁移、运行、CDC 三种权限分开，降低误操作面。

管理端的跨库视图

smartlect_admin 里有四个 SQL SECURITY DEFINER 视图，跨库聚合销售、商品销量、库存风险与售后履约。它们让 admin 只读访问分析数据，而不需要把业务库的写权限交给管理端。视图定义在主库迁移里，读的时候注意它们绕过调用者的库权限，属于需要重点审计的 SQL。

✗ 三个数据模型误区

① "同一个 MySQL 实例就是一个库"：不是。八个业务 schema，各自的 Flyway 与账号边界。
② "pay_order_id 是外键"：不是。它是订单与支付单的逻辑关联列，支付单在另一个 schema。
③ "订单退款就代表库存已回补"：不是。订单聚合状态与退款 Saga 的 STOCK_PENDING 是两个字段。

自测：为什么 order_request_idempotency 的唯一键是 (user_id, command_type, idempotency_key)，而不是单独的 idempotency_key？

因为不同用户可能碰巧生成相同的键，不同命令（下单、取消、退款）也可能复用同一个键。把用户和命令类型放进唯一键，才能把"同一个用户的同一种命令"作为一个幂等域，避免跨用户/跨命令误重放。

如果购物车有两件商品

下单会按 productId 聚合成两张 order_info，共享同一个 payOrderId。券关系只挂在第一张子单上；支付成功、关单、退款都按 payOrderId 聚合处理。退款时则按 order_item_id 逐条走，所以"整单退"和"退其中一件"是两条不同的路径。

✦ 只记一件事

Java 是交易权威，但没有任何一个 Java 事务能覆盖全部交易。价格、库存、券、支付、订单各自拥有自己的库；一致性靠幂等键、状态 CAS、Outbox、补偿与对账一层层收敛。读代码时，先问"这一步的事实归谁"，再问"失败后谁来收敛"。

自测：一笔支付单对应两张子订单，用户只退其中一张，系统怎么处理？

退款按 order_item_id 发起，生成一条独立的 refund_request；支付服务退对应金额；订单服务把该明细置 REFUND，并按剩余 NORMAL 明细数把订单改成 PARTIALLY_REFUNDED 或 REFUNDED；库存按 refundRequestId 回补；只有整单全退且无剩余 NORMAL 明细时才退券。

调试配方

  1. 起基础设施

    docker compose -f deploy/compose.yaml up -d。确认 MySQL、Redis、RocketMQ、Nacos、ES、Canal、xxl-job 的 healthcheck 都通过。

  2. 起 Java 服务

    python3 scripts/runtime.py up；端口以 run/runtime.env 为准。先看网关 /actuator/health，再看各服务注册是否出现在 Nacos。

  3. 打一条下单请求

    用演示买家登录，拿 cookie；带一个 16–64 位的 Idempotency-Key 调 POST /api/order/postOrder。同键再发一次，观察 Idempotency-Replayed 与 409 分支。

  4. 看 Redis

    会话键 token:login:token:*、商品缓存 smartlect:product:detail:*、券缓存、MQ 幂等键、限流键。用 SCAN，不要 KEYS *。

  5. 看 Outbox 与补偿

    下单后查 local_message_outbox：应有一条 15 分钟关单消息；再查 order_request_idempotency 的状态与响应 JSON。

  6. 制造失败

    把库存改成 0、把券改成 CANT、让支付失败，分别观察 P5 补偿、超时关单、退款重试。失败路径比成功路径更能说明设计。

十道自测

1. 网关为什么不注入 X-User-Id？

客户端可以伪造；下游统一从 Sa-Token 会话取身份，网关只做会话键存在性检查。

2. 商品详情缓存为什么把库存清零？

库存变化快且是交易事实；缓存只存静态快照，命中后用库存 RPC 实时补齐。

3. 搜索为什么先查 ES 再回 MySQL？

ES 只做文本召回，返回最多 500 个 ID；分类、价格、排序、分页仍以 MySQL 为准。

4. 购物车为什么敢不锁库存？

它只是待结算清单；真正的校验与扣减在下单阶段，由商品快照与库存服务裁决。

5. 锁券与核销的区别是什么？

锁券是 NOUSE→CANT；支付成功才 CANT→USED。取消/关单把 CANT 退回 NOUSE。

6. 下单为什么不在方法上加 @Transactional？

方法里有远程调用；包住会长时间占用数据库连接。只有 P3 的本地写入用短事务。

7. 幂等账本的 COMPLETED 为什么不能独立提交？

业务回滚时账本不能留下假成功；COMPLETED 必须参与调用方事务。

8. 库存影响 0 行一定是库存不足吗？

不一定；也可能是幂等账本已处理或 SKU 不存在，调用方要结合上下文。

9. Outbox 能保证消息只发一次吗？

不能；它是 at-least-once，重复投递靠消费幂等挡住。

10. 订单已退款，库存一定回补了吗？

不一定；退款 Saga 可能还在 STOCK_PENDING，订单聚合状态与 Saga 状态是两个字段。

动手实验

  • 把同一 SKU 库存设为 1，用两个并发请求同时下单，观察一个成功、一个库存不足。
  • 用同一个 Idempotency-Key 发两次不同金额的下单请求，观察 409 指纹冲突。
  • 支付成功后手工重投 pay-success 消息，观察订单幂等跳过与券核销补做。
  • 分别发起部分退款和整单退款，观察订单状态、库存账本与券状态。
  • 停掉 ES，搜索是否回退 SQL LIKE；停掉 Redis，哪些能力降级、哪些 fail-closed。
  • 查 stock_change_record，把三种 business_key 对上三种场景。
