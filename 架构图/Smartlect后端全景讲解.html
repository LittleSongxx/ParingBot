Smartlect Java 后端全景讲解

这份文档只讲 Java 电商后端（backend/，9 个服务），不讲 Python 导购 Agent。 它不按「模块清单」平铺，而是先找到这套后端唯一的根约束，再由它一步步推出每个机制—— 每个机制都是上一个机制带来的新问题的必然后果。

根约束 → 因果链 贯穿案例：¥4169 的耳机 图可点击放大 窄屏下图可横向滚动 结论锚到 path:line 离线单文件，无外部依赖

1一分钟看懂这套后端

9 个 Spring Boot 服务、一服务一库、没有分布式事务框架。一个网关把两种流量分开： 逛店与答题走 Python 导购；改价格、扣库存、落订单只有 Java 能做。

这张图看不到的那件事：网关刻意不依赖 common 模块（smartlect-gateway/pom.xml 无 common 依赖）， 所以它读 Sa-Token 会话键是按字符串硬编码的键前缀（AuthGlobalFilter.java:31,33）—— 一旦哪个服务改了 sa-token.token-name，网关校验会静默失效，而编译期不会报错。

2根约束：这场交易里没有事务

一次成交要写 5 个不同的库——订单在 order、库存在 stock、券在 coupon、支付单在 pay、地址在 user。 MySQL 的事务边界到单个库为止。
所以：这套后端的全部复杂度，都是「没有一把锁能把 5 个库锁在一起」这句话的后果。
这张图看不到的那件事：两条链不是并列的。写侧的每一步都在给下一步制造问题， 而读侧的每一步都在「用旧换快」——第 5 章会看到，缓存里存的商品快照库存被刻意清零，正是因为库存不允许旧。
如果当初选了「上分布式事务框架」会怎样？

仓库里明确选了不这么做（README.md「关键决策」表：一致性 → 不用分布式事务框架，统一本地事务 + Outbox）。 理由与代价写在一起：双轨（框架 + 手工补偿）会让回滚边界不可推理；代价是要自建幂等、补偿与对账四件事，并且接受短暂不一致。

注意 backend/deploy/seata/ 是历史容器卷留下的空目录（root 属主），不在版本控制里，不是"正在用 Seata"的证据。

4入口：网关做什么、不做什么

网关只回答一个问题：「你有没有登录」。
「你是谁、你能不能做这件事」它不回答，也不向后面传——因为一旦网关下发身份头，下游就没有办法分辨这个头是网关写的还是攻击者伪装的。
这张图看不到的那件事：「校验通过」等于「什么都没发生」。 网关测试里有一条断言，专门验证鉴权关闭时它仍然剥掉全部保留头（AuthGlobalFilterTest.java:178-197）—— 因为剥头不是"顺手做的清理"，而是身份信任链的第一环。

案例在这里

演示买家登录后，浏览器带的是 httpOnly 的 token Cookie。 网关拿它去 Redis 查 token:login:token:{t}，命中即放行；后面每个服务再各自用 Sa-Token 注解确认"这个人是谁、能不能做"。

5商品、缓存与搜索：把「旧」关在能容忍旧的地方

商品详情是最热的读。做法是三级缓存——但缓存里存的是「库存被刻意清零」的商品快照， 每次命中都要再问一次库存服务。这不是疏忽，是设计：详情页几乎不变，库存每秒都在变，两者不能共用一套 TTL。

搜索：ES 只是个「ID 过滤器」

这两张图看不到的那件事：商品详情的读根本不校验状态。 下架（status=0）商品的详情接口仍然返回数据（ProductInfoServiceImpl.java:303 起，路径上只查布隆/缓存/DB，没有 status 断言）； 挡住它的是列表侧的 status=1 过滤、以及 ES 查询里的 term status=1——该商品不会被搜到、不会出现在列表，但拿着 ID 仍能打开详情页。

案例在这里

买家打开 350000232815799 的详情页：L1 命中（或 L2 命中回填 L1）→ 返回 SKU 列表（价格 4169.00）→ 再向 stock 补一次实时库存。 整个过程中，ES 完全没参与——只有搜索框才用它。

6购物车与结算：价格三个来源各管一段

购物车存 MySQL（不是 Redis），一行一个 SKU，唯一键 (product_id, hash, user_id)。 价格在这里有三个来源，各管一段，不能混。
这张图看不到的那件事：「勾选」不是后端状态。购物车没有勾选接口，用户勾了哪几件是前端本地状态， 下单时把选中的明细列表整个传给 order 服务。所以后端永远不知道"购物车里当前选中了什么"——少了一份状态，也少了一份不一致。

7下单五阶段：三条纪律决定了一切

下单是整个后端最复杂的一段。它在代码里被明确切成五个阶段，注释写着为什么（OrderCreationService.java:100-102）。 三条纪律：① 本地事务里不许有远程调用；② 成功口径 = 短事务提交那一行；③ Phase 4 失败不回滚订单，而是补偿 + 15 分钟后收敛。
这张图看不到的那件事：「接口返回失败」与「订单已存在」可以同时为真。 Phase 3 提交后订单就真实存在了；如果 Phase 4 扣库存失败，用户看到的是失败，但库里躺着一张 15 分钟后被关闭的待付款单。 这就是为什么必须有「幂等账本」——它让重试不会变成第二张订单（第 9 章），以及为什么库存回补要校验 order-deduct 账本（第 8 章）。

拆单与金额：一个支付单，多张子单

  • 拆单规则：同一 product_id 归一张订单，不同 product_id 拆成多张子单；多 SKU 是同一张单下的多个明细行。
  • 它们共享一个 payOrderId：支付、取消、关单、退款都按支付单聚合（OrderFacts.loadOrdersByPayOrderId）。
  • 券的分摊按 orderId 排序，逐单吃掉优惠额（确定性顺序），再对最低实付兜底（末单补差）。
  • 实付再分摊到明细：支付成功时按原价权重把实付摊到每个 order_item，用累计取整让分差被最后一行吸收（否则退款会多退或少退几分钱）。
  • 金额单位：主链路用 decimal(10,2) + BigDecimal；只有 V2 报价确认链路用 long 分。全模块没有 double/float；DB 上还有 CHECK 约束兜底（paid_amount ≤ item_amount、refunded_amount ≤ paid_amount）。

8库存：把判断塞进一行 SQL

整个 stock 服务只有两张表，Java 侧零 Redis。防超卖靠的不是分布式锁，而是把「够不够」写进 UPDATE 的 WHERE 里， 让 MySQL 的行锁替你做那一次原子判断。

这张图看不到的那件事：批量扣减的账本信息是有损的。校验存在性的那把键只记录了第一个 SKU 的 productId/hash 与全部 SKU 的数量绝对值之和， 不足以逐 SKU 对账。所以一旦该键被人工清理或提前写入，回补就可能虚增或漏补——这是这条链上最脆的假设（第 18 章）。

9幂等账本：拒绝执行的艺术

大多数人以为幂等是「同一次请求重复执行不会出错」。这里的实现更保守： 同一个幂等键只会被执行一次，之后所有请求拿到的都是第一次的结果或道理——包括失败。 键不合法直接 400；键相同但请求体不同，409。

案例在这里

买家点了两次「提交订单」（或网络超时后重试）：第二次带着同一个 Idempotency-Key 与同样的 body， 命中 COMPLETED 后直接回放第一次的支付表单。库存只扣了 1 件，券只锁了 1 次，支付单只有 1 张。 若第二次的 body 变了（比如改了收货地址），返回 409 而不是默默用新地址下单。

10Outbox：让消息和本地事务同生共死

根约束的第二层后果：本地事务提交了，消息可能没发出去。 解法是「先把消息写进同一个库的 local_message_outbox 表，提交后再异步发」—— 事件因此获得了与业务数据完全相同的生死。
这张图看不到的那件事：「同键必须同语义」这条断言会把业务事务整体炸掉。 事件键设计错一次，不是「消息发重了」，而是下单/退款事务直接回滚。 退款回补键之所以带「轮次」refund:stock:{id}:attempt:{n}:ep{updatedAt}，就是因为人工审批会把 retry_count 归零， 只按 attempt 组键会命中旧轮的同键同载荷，静默什么都不发（MqIdempotencyKeys.java:33-42）。

11状态机与锁：并发由谁裁决

三条并发流会同时推同一张订单：支付回调、用户取消、超时关单。 裁决分两层：状态机决定「这个事件允许不允许」，支付单生命周期锁决定「同一时刻只有一条流在处理这个支付单」。

支付单生命周期锁：唯一的互斥枢纽

  • 粒度：按 payOrderId（一张支付单 = 一次结算，可能含多张子单），Redisson RLock。
  • 看门狗续期：不用固定过期时间，避免「业务还没做完锁先过期」。
  • 事务提交后才释放：否则下一个拿锁的流会读到未提交的状态。
  • 拿不到锁怎么办：抛 PayOrderLifecycleBusyException，让 MQ 重投来兜（消息侧有 5s/30s/120s 重试链）。
  • 它保护什么：支付回调、用户取消、超时关单三条流对同一支付单的读-判-写序列。
这张图看不到的那件事：状态机本身不保证并发安全，CAS 才保证。 所有写状态都走 update ... where order_status = 旧态，所以「两个流同时迁移」的结果是一个成功、一个 0 行—— 而 0 行之后做什么，取决于那个调用方（见上图红字）。

12超时关单与 24 小时墙

关单不用扫表，用 RocketMQ 的任意精度定时消息；但 broker 的时间轮有上限（默认 24 小时）， 而「7 天后自动收货」远超它——于是有了驻留（park）：不到时候不发，到点前再投一次。

关单要回滚四件事，而且每一步都独立容错

顺序动作失败会怎样
1Redis 一次性关闭标记（setIfAbsent + TTL）重复关单被这道标记挡住，是幂等去重
2payRpcSupport.markClosed 标记支付单关闭失败不改「已关」事实，靠支付轮询兜
3渠道侧关单 cancelOrder4Channel失败由支付轮询 / 退款对账兜底
4解券：CANT → NOUSE（仅这个状态）失败落补偿台账，重放走同一条幂等链
5还库存：restoreOrderStock（键 = payOrderId）失败落补偿台账；回补前置校验扣减账本

任何一步失败都不改变「订单已关」这个事实——收敛靠补偿台账自动重放（mqCompensationReplay，每分钟一轮）。

13支付、迟到支付与退款

支付是模拟的（无真实资金），但流程一步不少：渠道先落库、再发事件，order 侧收到事件后先远程核对、再改状态。 最值得看的是那条「钱付了、单已经关了」的路。
这张图看不到的那件事：支付「渠道」是一张枚举，不是一张表。当前只剩一个成员 MOCK； 历史落库的渠道名已不在枚举里，就成了「退役渠道」——解析时直接抛「不支持的支付渠道」， 而且这个判断被刻意放在归属校验之前：退役渠道在碰任何 bean / 网络之前就被拒（PayInternalService.java:75-84，2026-10-16 审计）。

案例在这里

买家点「模拟支付」：pay 落 pay_trade_record.trade_status=1 → 发事件 → order 收到后核对 → 订单 WAIT_PAYMENT→PAID， ¥4164.00 按原价权重摊到这一条明细上（单明细单，直接全额）→ 券 CANT→USED， 同时那条 15 分钟关单消息到点后发现「已付款」直接跳过——它不需要被撤回，只需要被忽略。

14优惠券：一个状态值承担了两段语义

券的实例状态只有四个值，而 CANT（"已作废"）被复用来表示「下单占用中」。 这是全文最值得警惕的一处设计：它让锁券、解锁、核销三条路径共用同一个状态值，也让「券卡在 CANT」成为最有特征的故障形态。
这张图看不到的那件事：「券停在 CANT」曾经是这套系统最有特征的故障形态。 顺序是锁券（CANT）→ 支付成功（订单变 PAID）→ 核销（CANT→USED）；最后一步在事务外，失败后事件重投会命中 「已支付」早退分支。2026-10-17 修复：早退分支现在会幂等补一次核销（普通单）/补一次激活（秒杀单）； 退款还券的消费失败也落进了 coupon 自己的补偿表，可按开关自动重放。排查信号不变： 订单已付款 + use_time 为空 + order_coupon_rel 有记录。

15身份与权限：网关不背书，服务端说了算

因为网关剥掉了所有身份头，下游只有两个合法的身份来源：自己内省 Sa-Token 会话（浏览器流量）， 或者走内部面并带上共享令牌 + 委托身份头（服务间/助手流量）。除此之外的任何「我是谁」都不可信。
这张图看不到的那件事：C 端根本没有角色表。「访客 / 演示买家」这两个身份的权限差异是按 userId 硬编码判定的 （TrialIdentities.java:14-70），不是查库得来的。对一个演示系统这是合理简化， 但它意味着「给某个真实用户加一个 role」这件事在这里没有地方可做。

16五层防线：每一层都有人负责收敛

把前八章分散的机制收成一张图。判据不是「有几层」，而是「每一层失败时，谁来把它拉回来」—— 没有收敛者的层就不是防线，只是愿望。
这张图看不到的那件事：「按库」这个语义在三处并不重合。 local_message_outbox 存在于 6 个库（order/user/product/cart/pay/admin），所以兜底扫描要登记 6 份； mq_compensation_log 只在 5 个库有表（order/product/user/admin/stock）—— coupon / pay / cart 有消费者或有 outbox，但没有审查表落库；而 mqCompensationReplay 只登记在 order 组。 这三处不重合是排查时最容易迷惑的地方。

17运维与门禁：注解不等于在跑

16 个定时任务、两条 CI 线（主链 + 只读应急）、三节点集群。这一章的核心事实是： 几乎所有「配置好了」的东西，都需要第二道登记或第二遍核对才算真的生效。
这张图看不到的那件事：xxl-job 的坑在「回拨地址」。 本地形态下调度中心在容器里、应用在宿主机，执行器必须自报 http://host.docker.internal:<port>； 否则调度照常触发、任务全部只触发不执行（handle_code=0）——没有任何报错，也没有任何日志。 这是 2026-10-16 故障演练顺带定位的真实缺陷。

18已知边界、本轮修复与仍存在的接缝

这一章分三段：仓库自己承认的边界（照抄 README「已知边界与遗留」）、 本轮（2026-10-17）已修复的接缝（每条都有回归测试）、仍然存在、需要产品/运维决策的接缝。 每段都标了证据位置，可以自己复核。

一、仓库自述的边界（README「已知边界与遗留」）

二、本轮已修复（2026-10-17，均有回归测试）

1 · 券核销/激活没有收敛者。 支付事件重投会命中「已支付」早退分支，而券核销在事务外——失败后再也不会执行，券永久停在 CANT。 现在早退分支会幂等补一次核销（普通单）/补激活（秒杀单），并排除已全额退款（REFUNDED）的订单。 OrderPaymentService.java · 回归 OrderPaymentServiceTest（4 例）。

2 · C 端 IP 可伪造。 三处旧实现（登录锁定、限流切面、文件上传）都取 X-Forwarded-For 第一段；2026-10-16 的审计只加固了 IpUtils，而它当时只有管理端登录一个调用方。 现在三处统一走 IpUtils.resolveClientIp，并给 4 位数字验证码接口加了 IP 限流（60s/30 次）。 回归 IpUtilsTest（6 例）。

3 · 退款还券的消费失败没有落点。 coupon 库补了 mq_compensation_log（V3）并登记 mqCompensationReplay； 新增开关 mq.compensation.auto-replay-consume，只对 coupon（还券幂等）打开，其它域保持人工。 回归 MqCompensationLogServiceImplTest（3 例）。

4 · 管理端写接口没有权限注解。 19 个写方法补齐 @SaCheckPermission（发货/封禁/分类/物流/审核/地址/上传/商品写），新增 user:manage、settings:manage、moderation:manage 三个权限点（V5 只授超管）。 CI 门禁不再接受「登记在展厅拒绝清单」作为保护证明，并拒绝只写 admin:trial 的写接口。 展厅的退款复核与读页面不受影响（拒绝清单仍在，注解都是方法级）。

5 · 通配绑定 + actuator 暴露。 生产就绪模式下，server.address 为空/0.0.0.0/:: 且 actuator 暴露 prometheus 会拒绝启动； 留 smartlect.allow-wildcard-bind 作为集群的显式确认（集群脚本已写入），README 补了安全组核对项。

6 · 索引每次启动全量重建。 改为先比较 ES 文档数与在售商品数：缺文档（或索引为空/读不到）才重建，多余文档不触发； 等量内容陈旧需显式 smartlect.canal.index-force-rebuild=true。 回归 ProductIndexInitializerTest（7 例）。

三、仍然存在的接缝（我的观察，附证据）

1 · 商品详情不校验上下架。 getProduct4VOByProductId 路径上只做布隆过滤器 + 缓存/DB 查询，没有 status 断言 （ProductInfoServiceImpl.java:303）。挡住下架商品的是列表侧 status=1 与 ES 的 term status=1： 搜不到、列表不出现，但拿着 ID 仍能打开详情页。是「入口收敛」还是「遗漏」取决于产品意图，代码里没有说明。

2 · 网关白名单是整前缀放行。 application.yml:208-222 的 web-exclude-paths / admin-exclude-paths 按前缀匹配 （如 /api/product/**）。把一个新的写接口放进已放行的前缀下，它会静默变成免鉴权接口——除非服务端自己有注解。注释里已提醒这一点。

3 · order_info 三列金额是「假列」。 goods_amount / discount_amount / coupon_discount 在 DDL 里（V3__baseline.sql:6-8）， 但 resultMap 不映射、下单也不写；真正的抵扣在 order_coupon_rel。按列取数会得到 0； 报表视图用的是 order_info.amount，所以目前不影响看板。删除列属于破坏性 schema 变更，留给后续决策。

4 · 批量扣库存的账本信息有损。 账本只记录第一个 SKU 的 productId/hash 与全部变更量的绝对值之和（SkuStockService.java:298-309）， 无法逐 SKU 对账。它是「关单回补前必须证明扣过」这条链最脆的假设；当前没有逐 SKU 对账的读者，所以还没咬人。

5 · 展厅写白名单在运行时不起作用；另有一处死方法。 ALLOWED_WRITE_PATTERNS 只被 CI 脚本与测试消费，运行时 allows() 只看拒绝清单—— 「退款复核被显式放行」的真实原因是它没被拉黑。RemoteCompensateRecorder.recordStockChangeBatch 只有定义、无调用方。 两者都不影响当前行为，但会误导下一个读代码的人。

三类分开写的原因：仓库自述的边界是「已经想清楚并接受的取舍」； 已修复项有代码与测试支撑，可以按 path:line 复核；仍存在的接缝是「还没被处理的差异」， 其中有的需要产品决策（详情页是否该挡下架）、有的需要 schema 变更（假列）、有的只是文档债（白名单语义）。 前两类不该被当成缺陷来指责，第三类也不该被当成「设计如此」来略过。

19一句话串完，再给一张反向索引

一次成交要写 5 个库，而没有一把锁能锁住它们——这是唯一的根约束。
于是：本地事务 + 同库落盘的事件（Outbox）；投不出去就租约重试、每库一份兜底扫描；消息重复就消费幂等租约； 调用方重试时没人知道成没成，就用幂等键 + 载荷指纹 + 409，答不上来就升级 INCONCLUSIVE 交给人； 库存只靠一行 WHERE 防超卖，扣了就要能凭账本安全还回去；多条并发流靠状态机 CAS 与支付单锁裁决； 15 分钟关单、7 天收货靠延迟消息，越过 broker 24 小时上限就驻留。
读侧相反，它用旧换快：缓存里库存清零、价格库存不进向量、ES 只当 ID 过滤器（甚至默认关掉分词）。 这些取舍都不优雅，但每一个都指着一个明确的收敛者——要么自动重放，要么落到人必须看的那个计数上。
